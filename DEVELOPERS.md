# Asterion Solver: developer guide

How to embed the solver in other programs, build it, and release it. For using the command line tool,
see the [README](README.md).

## Using the library

The library is the `asterion-core` module. Until it is published, install it in your local Maven
repository with `./gradlew publishToMavenLocal`, then:

```kotlin
dependencies {
    implementation("me.champeau.asterion:asterion-core:0.1.0-SNAPSHOT")
}
```

```java
PlateSolver solver = PlateSolver.open(Path.of("tycho2.astx"), Path.of("gaia-500.astx"));

// from a FITS file
SolveResult result = solver.solve(Path.of("image.fits"), SolverOptions.defaults());
result.solution().ifPresent(solution -> {
    System.out.printf("%.5f %.5f, %.3f\"/px%n", solution.raDeg(), solution.decDeg(), solution.pixelScale());
    double[] sky = solution.wcs().pixelToSky(1024, 768);
    Map<String, Object> keywords = solution.wcs().toFitsKeywords();
});

// from pixels: an image of floats, which is left untouched
GrayImage image = new GrayImage(width, height, floats);
result = solver.solve(image, ImageHints.none(), SolverOptions.defaults());

// from samples in memory, such as the frame of a camera: copied, converted and binned in one pass, into an
// image which the solver then uses as working memory
GrayImage copy = RawPixels.read(segment, RawPixels.SampleType.UINT16, width, height, rowStride, bayer, 0);
result = solver.solveInPlace(copy, ImageHints.none(), SolverOptions.defaults(), 0);

// from stars detected by other means, sorted by decreasing brightness
result = solver.solve(StarList.of(x, y), width, height, ImageHints.none(),
        SolverOptions.builder().position(83.8, -5.4, 5).scale(0.9, 1.1).build());
```

Installing a catalog reports its progress to a `ProgressListener`, which applications implement to show
progress their own way. All its methods are optional:

```java
Catalogs.install(Catalogs.find("tycho2").orElseThrow(), Catalogs.defaultDirectory(), new ProgressListener() {
    @Override
    public void advanced(ProgressUpdate update) {
        // update.step() describes the step: "Downloading Tycho-2...", 21 "files"
        progressBar.setValue(update.fraction());
    }
});
```

`ProgressListener.text(System.out::println)` prints progress the way the command line tool does, and
`ProgressTracker` reports the progress of a step, from any number of threads, for those who write their own
catalog descriptors.

A `PlateSolver` is thread-safe. Opening an index is immediate, since index files are memory mapped.
Catalogs can be installed programmatically with `Catalogs.install(...)`, and custom indexes can be built
from any list of stars with `IndexBuilder`. The library requires Java 25.

### From C, C++, Python...

The `asterion-lib` module builds Asterion as a native shared library, which programs in any language able to
call C functions use to install catalogs and solve the images they have in memory: see
[asterion-lib/README.md](asterion-lib/README.md). Python programs use it through the Python package,
`pip install asterion-solver`: see [its documentation](asterion-lib/src/main/python/README.md).

## Project structure

- `asterion-core`: the library. The search is in the `solver` package: `PlateSolver` tries stages of searches,
  from the quickest to the most tolerant, `QuadSearch` matches the quads of the image with the ones of the
  index and `Refiner` fits the solution; `WideField` searches the images of wide angle lenses, whose
  projection stretches the shapes of quads away from the center, in a stereographic projection of the image
  for a range of focal lengths, with the quads of the index which are wide enough, which `index.WideQuads`
  keeps in a file next to the index. Its table of deep sky objects (Messier, NGC, IC, Sharpless, van den Bergh,
  LBN, LDN) is generated from OpenNGC and VizieR by `asterion-core/src/dso/GenerateDeepSkyObjects.java`, see
  [its README](asterion-core/src/dso/README.md). Its tests solve real images against a small index of their
  fields, see [asterion-core/src/testdata/README.md](asterion-core/src/testdata/README.md)
- `asterion-web`: the web interface, with the HTTP server of the JDK and a page without dependencies. Its sky
  data (constellations, bright stars) is generated by `asterion-web/src/sky/GenerateSkyData.java`, see
  [its README](asterion-web/src/sky/README.md)
- `asterion-cli`: the command line tool, including the [ASTAP compatibility mode](docs/astap-interface.md)
  in the `me.champeau.asterion.cli.astap` package
- `asterion-lib`: the native shared library, see [From C, C++, Python...](#from-c-c-python): its functions,
  in `NativeLibrary`, read and write the structures of `src/main/c/asterion.h`, described by `CStructs`. The
  Python package, `src/main/python`, wraps them, and `PythonWheel`, in `build-logic`, writes its wheel
- `build-logic`: the build conventions, an included build
- `benchmarks`: the [comparison with other solvers](benchmarks/README.md)
- `integrations`: the scripts for [PixInsight](integrations/pixinsight/README.md) and
  [Siril](integrations/siril/README.md)
- `docs`: specifications, such as the [interface of ASTAP](docs/astap-interface.md) which the compatibility mode follows
- `site`: what GitHub Pages serves, such as the PixInsight update repository of the script, see
  [Publishing the PixInsight script](#publishing-the-pixinsight-script)

## Building

The build requires a Java 25 installation, which Gradle finds as a toolchain. The native executable is
built with Oracle GraalVM 25.4, an innovation release, on every platform: GraalVM 25.0 loses the accents
of command line arguments on Windows. Download it from [graalvm.org](https://www.graalvm.org/downloads/),
and point `GRAALVM_HOME` to it. There is no GraalVM 25.4 for macOS on Intel, which isn't supported anymore.

```
./gradlew test                  # compiles, and runs the tests of the JVM
./gradlew build                 # also checks the formatting and tests the native library, requires GraalVM 25
./gradlew nativeCompile         # builds the native executable, requires GraalVM 25
./gradlew nativeZip             # packages it for the current platform, with the web interface
./gradlew :asterion-lib:nativeLibrary  # builds the shared library and its headers, in asterion-lib/build/native-library
./gradlew :asterion-core:jmh -Pjmh.includes=Decode   # microbenchmarks of the hot loops, see asterion-core/src/jmh
./gradlew installDist           # JVM distribution, in asterion-cli/build/install
./gradlew test jacocoTestReport # coverage of the tests, in <module>/build/reports/jacoco/test/html
```

The tests of the native library, `./gradlew :asterion-lib:nativeLibraryTest`, which `check` and `build` run,
build the shared library, then compile programs in C against it and run them: the programs are compiled with
`cc`, or with Visual C++ on Windows, which the build sets up the way native-image does. Where Python is
installed, they also install the wheel of the Python package in an environment of their own, as `pip` installs
it from PyPI, and run its tests, `asterion-lib/src/test/python`, against it. CI runs them with the oldest
version of Python which the package supports.

The Python package, `asterion-lib/src/main/python`, calls the library with `ctypes`:
`./gradlew :asterion-lib:pythonWheel` writes its wheel for the current platform, with the library, to
`asterion-lib/build/python`. The wheel works with Python 3.10 and later, and its tag tells the platforms where
the library runs: the oldest glibc it needs on Linux, the oldest macOS it supports. `./gradlew -p build-logic test`
tests the code of the build, which `check` runs too.

The native executable is `asterion-cli/build/native/nativeCompile/asterion`, a single file: images are
decoded by Asterion itself, not by AWT, which native images don't support on every platform. The
executable targets any x86-64 or ARM64 processor by default: `-PnativeMarch=native` optimizes it for the
build machine.

The native executable is built with profile-guided optimization, when the build runs with Oracle GraalVM:
the profile is `asterion-cli/src/pgo-profiles/main/default.iprof`. It halves the size of the
executable, and makes it 3% (typical solve) to 10% (index building, exhaustive searches) faster.
`./update-pgo.sh` regenerates the profile from a workload of your choice, which is worth doing when the
solver changes significantly. The native library has a profile of its own,
`asterion-lib/src/pgo-profiles/main/default.iprof`, which `./update-library-pgo.sh` regenerates: an
instrumented build of the library solves the images it's given, handed over as the samples programs have in
memory.

## Image decoders

PNG, JPEG, TIFF and BMP images are decoded by Asterion, and must give exactly the pixels which ImageIO
gives: the brightness of a pixel is the sum of its color channels. JPEG images are decoded like the IJG
library which the JDK uses, see [third-party/ijg-libjpeg.md](third-party/ijg-libjpeg.md), and YCbCr ones
give their luma: the decoder reads that component alone, which skips the chroma scans of progressive files,
the upsampling and the color conversion, and must match the raw luma ImageIO gives with `readRaster`. Color
profiles are ignored, unlike ImageIO which applies some of them.

`ImageDecodersTest` checks every variant ImageIO writes, and damaged files. Two more tests take a list of
image files, one path per line, to check real images:

```
./gradlew :asterion-core:test --tests '*ImageCorpusTest' -PimageCorpus=images.txt          # same pixels as ImageIO
./gradlew :asterion-core:test --tests '*ImageDecodersBenchmark' -PimageBenchmark=images.txt # time compared with ImageIO
```

Their reports are written to `asterion-core/build/reports/image-corpus.txt` and `image-benchmark.txt`.

## Formatting

`./gradlew format` formats the Java sources and adds the license header to new files; `./gradlew check`
fails when a file isn't formatted. The rules are an Eclipse formatter profile,
[`config/formatting/eclipse-java.xml`](config/formatting/eclipse-java.xml), which IntelliJ IDEA can import
(Settings > Editor > Code Style > Java > Import Scheme > Eclipse XML Profile). Among them:

- 4 spaces of indentation, 8 for continuation lines, and lines of at most 140 characters;
- record components and enum constants one per line;
- line breaks made by hand are kept, and comments aren't reformatted;
- `// @formatter:off` and `// @formatter:on` exclude code from formatting.

The formatter wraps a call which is too long before its method name when it can't wrap between its
arguments: wrapping it by hand where it reads best is kept.

## Publishing catalogs

Users download catalogs already indexed, from the releases of
[asterion-solver/catalogs](https://github.com/asterion-solver/catalogs/releases). There is a release per
version of the format of index files (`StarIndex.VERSION`), named `catalogs-v<version>`: each version of
Asterion downloads the files it can read. A release contains the indexes compressed with gzip, split in
parts of less than 2 GB for GitHub, and a manifest, `catalogs.properties`, which lists their sizes and
SHA-256 checksums. Catalogs which aren't published, or can't be downloaded, are built from their sources.

`./publish-catalogs.sh` builds the published catalogs from their sources, packs them and uploads them with the
GitHub CLI, which must be logged in with the right to create releases in the organization. It needs about 30 GB
of disk space and 8 GB of memory, more for `gaia-3000`, and works in `build/publish-catalogs`: when it's
interrupted, running it again resumes the downloads. It must run again when the format of index files changes,
which creates a new release, or when the indexes change.

The catalogs which are published already are kept as they are, unless their index is in
`build/publish-catalogs/catalogs`: a catalog is added to the release by adding it to the list of the script,
and its index to that directory when it was built already. `DRY_RUN=1` stops the script before it uploads
anything, with the files to publish in `build/publish-catalogs/release`.

The script uses two hidden options of the command line tool:

- `--from-sources` builds indexes from the stars of the catalogs, instead of downloading them already indexed;
- `--pack-catalogs <directory>` writes the compressed parts of the installed catalogs, and their manifest.

## Publishing the PixInsight script

The PixInsight script is installed from a PixInsight update repository,
`https://asterion-solver.github.io/asterion/pixinsight/`: the `site/pixinsight` directory, which the `Site`
workflow deploys to GitHub Pages when it changes on `main`. GitHub Pages must use GitHub Actions as its
source (Settings > Pages). The repository is an index, `updates.xri`, and the package of a version, a zip of
the files which PixInsight installs, relative to its installation directory.

After a release, its package is written with:

```
integrations/pixinsight/build-repository.py 0.3.0
```

It packages the script and the license of the tag of the release, `v0.3.0`, stamped with the version, and
dates the package with the publication of the GitHub release, which it reads with the GitHub CLI. The
package is deterministic: PixInsight knows whether a package is installed by its SHA-1, so building the
same release again gives the same package, which PixInsight doesn't offer again. The index lists only the
new package, and the previous ones are removed: PixInsight installs every listed package which isn't
installed, in no defined order. Committing and pushing `site/pixinsight` publishes it.

`--working-tree` packages the script of the working copy instead, to test a package: `--output` writes it
elsewhere, such as a directory served by `python3 -m http.server`, which PixInsight accepts as a repository at
`http://localhost:8000/`.

The repository isn't signed yet. Signing will be added to `build-repository.py`, with the keys of a Certified
PixInsight Developer: the script gets an `.xsgn` signature in the package, and `updates.xri` a signature of
its own. Both are made by PixInsight itself, on the machine which holds the keys.

## Testing a build before releasing

The `Build` workflow runs for each push to `main`, each pull request, and on demand. It builds and tests the
native executable on every platform, and uploads the archives as artifacts of the run, named
`native-<platform>` (`native-windows-x86_64`, `native-osx-aarch_64`…), which are kept 90 days, with the native
library, `library-<platform>`, and the wheel of the Python package, `wheel-<platform>`, which `pip install` takes. It then builds
and tests the N.I.N.A. plugin with the Windows library of the same run, and uploads it as `nina-plugin`. Nothing
is released. To test the Windows archive of the last build of `main`:

```
gh run download --repo asterion-solver/asterion -n native-windows-x86_64 \
  $(gh run list --repo asterion-solver/asterion --workflow Build --branch main --limit 1 --json databaseId --jq '.[0].databaseId')
```

To build a branch without merging it: `gh workflow run Build --repo asterion-solver/asterion --ref <branch>`,
then download its artifacts the same way. In a browser, the artifacts are at the bottom of the page of the
run, in the Actions tab: GitHub wraps them in another zip archive.

## Releasing

Releases are made with the `Release` GitHub workflow, started by hand with the version to release
(for example `1.0.0`). It builds and tests the native executable on Linux (x86-64 and ARM64), macOS
(Apple Silicon) and Windows, then [JReleaser](https://jreleaser.org) tags the current commit
and publishes a GitHub release with one zip per platform, their SHA-256 checksums and a changelog
built from the commit messages (the `conventional-commits` preset groups `feat:`, `fix:`... commits). Each zip
contains both executables: `asterion-web` is bundled in the archive of `asterion-cli` by its
`bundledExecutables` dependencies.

The version of `gradle.properties` is always a snapshot: the released version is given to the build with
`-Pversion`. Once the release is published, the workflow sets it to the next development version and
pushes that commit, as `github-actions[bot]`: `0.1.1-SNAPSHOT` after `0.1.0`, `1.0.0-SNAPSHOT` after
`1.0.0-rc.1`. A higher version which was set by hand, when the next release adds features for example,
is kept. The name of the executable and of the archives is the `executableName` property of
`gradle.properties`.

Two properties help performance experiments on the native executables: `-PnativeMarch=native` tunes the code
for the build machine (portable `compatibility` code by default), and `-PnativeExtraArgs="…"` passes other
`native-image` options, such as `-H:-GenLoopSafepoints` or `--gc=epsilon`. Measure with fresh processes, one
image at a time, as SharpCap runs the solver: a warm process is noticeably faster than a cold one, and JVM
timings, even with the Graal JIT, don't transfer to the native executable. The N.I.N.A. plugin is the warm case:
it keeps the library loaded, and its catalogs open, between solves.

To check the release configuration locally, put archives named like the ones of the workflow in an
`artifacts` directory, the library archive included, and run:

```
JRELEASER_GITHUB_TOKEN=dummy ./gradlew jreleaserFullRelease --dryrun -Pversion=1.0.0
```

### The Python package

A release also publishes the wheels of the Python package to PyPI, as
[`asterion-solver`](https://pypi.org/project/asterion-solver/), with trusted publishing, without any secret: PyPI
trusts the workflow `release.yml` of the repository `asterion-solver/asterion`, with its environment `pypi`, to
publish it, as its publisher on PyPI tells. The versions of the package are the ones of the project, written the
way of Python: `1.0.0-rc.1` is `1.0.0rc1`, so the pre-releases are `alpha`, `beta` or `rc`, which the workflow
checks before building anything. The next development version is committed once the release is published to
GitHub and PyPI: if PyPI fails, re-running the failed jobs of the workflow publishes it again.

### The native library

A release also publishes the native library, see [asterion-lib/README.md](asterion-lib/README.md), apart from
the archives of the application, which don't contain it: one archive, `asterion-library-<version>.zip`, with a
directory per platform, so that the release page lists a single archive for developers. Each platform packages
its library with `nativeLibraryZip`, and the release workflow gathers them with `nativeLibraryBundle`, with
the documentation of the library and the licenses.

### The N.I.N.A. plugin

A release also publishes the N.I.N.A. plugin, `asterion-nina-<version>.zip`, built with the Windows library of
the same run. N.I.N.A. users get it once its manifest is merged into the plugin repository of N.I.N.A.,
[isbeorn/nina.plugin.manifests](https://github.com/isbeorn/nina.plugin.manifests), where its maintainers review
it. Not every release matters to N.I.N.A. users, so it is proposed by hand: run the `N.I.N.A. plugin manifest`
workflow (Actions > N.I.N.A. plugin manifest > Run workflow) with the released version, and check
`pull-request`. It writes the manifest from the published zip, with `integrations/nina/New-NinaManifest.ps1`,
in place of the manifest of the previous release, since the plugin repository keeps a single manifest of the
plugin. It validates it with the scripts of the plugin repository, which also download the zip to check its
checksum, and opens the pull request from a fork. Don't propose pre-releases: their plugin has the version of the
next release.

Opening the pull request needs, once:

- a fork of `isbeorn/nina.plugin.manifests`, whose name, such as `owner/nina.plugin.manifests`, is the repository
  variable `NINA_MANIFESTS_FORK` (Settings > Secrets and variables > Actions > Variables);
- a personal access token of the owner of the fork, the repository secret `NINA_MANIFESTS_TOKEN`. A fine-grained
  token, limited to the fork with the permission Contents: Read and write, pushes the branch of the manifest to the
  fork: the run then gives the link which opens the pull request, since fine-grained tokens can't contribute to
  repositories of other owners. A classic token with the `public_repo` scope also opens the pull request, but it
  can write to all the public repositories of its owner.

Without them, the workflow only validates the manifest, and uploads it as the artifact `nina-manifest` of the
run, to propose by hand. With `pull-request` unchecked, it only checks the manifest of a release, without
proposing it.
`New-NinaManifest.ps1` runs locally too, with PowerShell 7:

```
pwsh integrations/nina/New-NinaManifest.ps1 -Version 0.3.0 -Zip asterion-nina-0.3.0.zip -Output manifest.json
```
